# Correction learning for pasted dictation (Windows UI Automation)

- `TextPattern.TextChangedEvent` means that textual content was modified. It is a notification, not an edit explanation: it does not say whether the change came from typing, paste, autocorrect, script, or an undo. After the event, re-read the control; Microsoft warns that existing `TextPatternRange` objects can become invalid when provider text changes. [TextChangedEvent](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.textpattern.textchangedevent?view=windowsdesktop-10.0)
- `TextPattern` exposes a text stream and ranges but is read-only for editing. A client can use `ValuePattern` or keyboard input where the target supports it, but should treat pattern availability as per-control capability rather than an assumption. [TextPattern overview](https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/ui-automation-textpattern-overview)
- Start from the element with input focus (`GetFocusedElement`) immediately after the paste, then verify it is an editable text/document element and that it supports `TextPattern` or `ValuePattern`. Focus can move or the element can disappear; handle `UIA_E_ELEMENTNOTAVAILABLE` and re-check. [Obtaining UI Automation elements](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-obtainingelements)
- Microsoft’s Edit control contract generally requires `TextChangedEvent` and `AutomationFocusChangedEvent`, but real targets vary. Electron/Chromium web editors, browser compose boxes, custom widgets, and remote/virtualized controls may expose incomplete or unstable UIA trees/patterns; failure to obtain a pattern should disable observation for that target rather than fall back to broad keystroke capture.
- Password edits are an explicit exclusion: when `IsPassword` is true, querying the Value is required to fail. Never inspect, diff, or learn from such controls. [Edit control support](https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/ui-automation-support-for-the-edit-control-type)
- A low-cost design is bounded post-paste observation: store a pending record containing the pasted transcript, target identity, timestamp, and (when safely readable) baseline text. Listen only briefly for `TextChangedEvent`; re-read current content and compute a stable range-aware diff. Ignore selection-only events, caret navigation, focus changes, and edits outside the pending window.
- Treat the paste callback/keyboard dispatch as intent only. Begin the pending window after confirming the focused target and observing the resulting readable content; compare later user edits with the final pasted text actually present in the control, rather than assuming the raw transcript was inserted unchanged.
- Treat a candidate as a suggestion, not an automatic dictionary update. Require a small localized replacement (for example, one token or short phrase), reject large rewrites and ambiguous diffs, keep only metadata plus the candidate by default, and ask the user to confirm before persisting a personal term. Do not claim knowledge of any third-party dictation product’s internals; this is a Windows UIA-based inference.

## Recommended operating rule

Observe only the known focused target for a short post-paste window. If the target cannot provide readable, non-password text and a reliable change notification, mark the observation unsupported and leave learning to explicit user confirmation (for example, a correction command or dictionary UI).
